The bottom line: about 7 in 8 people who create an account never come back on a later day. Most of the drop happens before the first return, so that is where to look first (the first-session experience and what brings someone back on day two). Beyond 3 return days the numbers are single people, too few to read anything into.

Data issues to raise with Samar

  1. GA4 keeps event data for only two months on this property. Admin → Data settings → Data retention is set to "2 months", so user-level analysis (funnels, cohorts, explorations) cannot see anything before Sep 11, 2026. That is why this report starts there. Switching it to 14 months takes one click and is free, but only protects data from now on. I did not change it.
  2. Milestone events go missing for some accounts. 13 accounts fired user_return_2d after signing up, but only 9 of them fired user_return_1d first; requiring the milestones in order would give 4.7% at 2+ and 1 at 4+ instead of 6.8% and 5. The likeliest cause is a return on another device or browser, which GA4 treats as a different person, or a blocked tracker. Ask Samar whether the GA4 user_id is set on every event once someone is logged in (only ~1,500 GA4 users carry one); that would let GA4 join devices. Until then, every number here is a floor: returns made only on a second device are invisible.
  3. Sign-up tracking has changed several times. In August account_created fired about 1.8 times per user (the duplicates Samar retired on Oct 8); from Aug 31 to Oct 4 only 7 to 22 people a week fired it while 65 to 115 entered onboarding; since Oct 5 it is about 1 per user and 18 to 36 a week. Worth checking against the app's own database: were sign-ups really that low in September, or was the event broken?
  4. Developer traffic lands in the production property. localhost (49 users firing account_created since July) and Vercel preview deploys report to it. This report filters to app.thoughtsaver.com; a GA4 data filter or a separate dev property would keep it clean everywhere.
  5. The full history may already exist in BigQuery. The property has had a BigQuery export since Sep 2022 (Google Cloud project 200310840257). Export tables are not subject to the two-month limit, and they hold per-user rows, so the same analysis could go back to July (when the return events started). I don't have access to that project; if Samar or Spencer can grant read access, this becomes a much bigger sample.

How this was measured

A sign-up cohort = people whose first visit fell in that Monday-to-Sunday week and who fired account_created on app.thoughtsaver.com (97% sign up on the day of their first visit). A person counts for "N return days" if they fired user_return_Nd at any point after account_created, the definition in Samar's spreadsheet (separate days, not necessarily in a row). Built with GA4 closed funnels, which follow each person, so returns from people who signed up earlier cannot leak in. Independent check: one pooled query per N over all weeks gave exactly the same totals as the per-week queries (all matched). Confidence intervals: Wilson 95%. Code: reports/thoughtsaver_retention_cohorts_2026-11-11_src/; tests: tests/test_thoughtsaver_retention_cohorts.py.
