Why GA4 purchases show (not set), and how to fix it

Clearer Thinking GA4 property, Stripe purchases. Generated 2026-09-11 10:51am

The purchase event is not sent by the buyer's browser. It is sent by a server (Paytics, listening to Stripe) that has never seen the buyer's browser, so it cannot tell GA4 which visit the purchase belongs to. GA4 credits a traffic source to a visit, not to an event. A server event that cannot be matched to a visit is filed under a phantom visit with no source, which GA4 shows as (not set).

The fix is to carry two numbers from the buyer's browser into the Stripe Checkout Session (the GA client_id and session_id) and have the Stripe webhook send those two numbers along with the purchase. Nothing in GA4's settings can fix it, and no thank-you page can fix it for two of the three paid flows.

1. How GA4 decides where a purchase came from

  • Two numbers in a cookie. When someone lands on clearerthinking.org, the Google tag writes two numbers in the browser: client_id (this browser) and session_id (this visit). Once per visit it also records where the visit came from: a Google ad, a newsletter link, organic search.
  • Events inherit the source from the visit. Any later event that arrives with the same two numbers is filed under that visit and inherits its source. GA4 does not store the source on each event; it looks it up from the visit.
  • Unknown numbers, new visit. An event that arrives with a made-up client_id and no session_id is filed as a brand-new visit. That visit has no landing page and no session_start, so it has no source. That is exactly the case Google's (not set) article describes.

The tell is in the screenshot: 32 purchases, 32 "total users". Every purchase arrives as a brand-new anonymous person.

2. What happens today

1. Visitor lands on clearerthinking.orgGoogle tag knows the source (say google / cpc) and writes client_id + session_id in cookies.
→
2. GuidedTrack programBuy button asks Firebase for a checkout link. The two GA numbers are not read.
→
3. Firebase creates the Checkout SessionNo GA numbers attached (metadata holds only product_key and email).
→
4. checkout.stripe.comStripe's domain. Our tags cannot run there, so the visit ends here for GA4.
→
5. Stripe webhook, then PayticsSends "purchase" to GA4 server-to-server with an invented client_id and no session_id.
→
6. GA4Creates a phantom visit with no session_start and no landing page. Source / medium: (not set).

The purchase never travels through the browser, so the information about the visit is never attached to it. It is not lost in transit; it was never there.

3. What the documentation says

Google Analytics

"Session source / medium will report (not set) for sessions where the automatically collected event session_start is missing."GA4 Help: What the value (not set) means in your reports. The fix suggested there (a Tag Manager trigger change) is about browser tagging and does not apply here: our purchase never goes through the browser.
"Both the session ID and session number are associated with each event in a session automatically via gtag.js and the Google Analytics for Firebase SDK. However, the identifier is not included automatically in events from Measurement Protocol or Data Import."GA4 Help: About Analytics sessions
"If you want a Measurement Protocol event to reflect geographic and device information from a specific session instead of the latest information for the client_id [...], then include session_id in the event and send it to Measurement Protocol within 24 hours of the start of the session." Also: "While it's possible to send events to Google Analytics solely with the Measurement Protocol, only partial reporting may be available."GA4 Measurement Protocol overview
"The client_id should match the ID generated by the Google Analytics tag on your website." Reference: session_id is "Required for several common use cases"; timestamp_micros may backdate an event "up to 72 hours".Sending events and Measurement Protocol reference
gtag('get', 'G-XXXXXXXXXX', 'client_id', callback) and the same with 'session_id' return the two numbers from the page.gtag.js reference, the get command

Stripe

"In Server-side event recording, you recorded the server-side metrics against an anonymous client ID. That ID is different from the one associated with the page view metrics, so Google Analytics has no way to link the page view and purchase metrics." Stripe's fix: read the ID with gtag('get', ..., 'client_id'), "Store the ID in the Checkout Session's metadata", then "Retrieve the ID and send it with the request to record the event" in the checkout.session.completed webhook.Stripe Docs: Analyze your conversion funnel with GA4. Note that Stripe's example passes only client_id. That links the buyer to the right person (first-user source) but not to the visit. For session source / medium GA4 also needs session_id; two independent test write-ups confirm client_id alone still gives (not set) at session scope (Simo Ahava, MetricFixer lab).
Metadata is one of the few fields that can be updated on an existing Checkout Session.Stripe API: Update a Checkout Session. This is what ct-checkout's stamp step relies on.
"You can't rely on triggering fulfillment only from your checkout landing page, because it's not guaranteed customers visit that page."Stripe Docs: Fulfill orders. Same logic applies to analytics: the webhook is the reliable place to record the sale.
Payment Links accept a client_reference_id URL parameter ("alphanumeric characters, dashes, or underscores, and be any value up to 200 characters") that "is sent in the checkout.session.completed webhook after payment completion."Stripe Docs: Track a payment link. Useful for the static buy.stripe.com links (donations, supporter tiers), not for the Firebase-created sessions.

5. The fix

1. Visitor on clearerthinking.orgUnchanged. Tag writes client_id + session_id.
→
2. GT program page reads the two numbersBridge script handler (get-ga-ids) or gtag('get'). Program stores them in variables.
→
3. Firebase creates the session with metadataga_client_id and ga_session_id set at creation (Stripe's own pattern). Alternative: ct-checkout stamps them onto the open session.
→
4. checkout.stripe.comUnchanged.
→
5. Webhook sends the purchase with the numbersclient_id + session_id + transaction_id + value, sent within minutes of the visit.
→
6. GA4Files the purchase under the original visit. Source / medium populated; channels, campaigns and Google Ads attribution work.

Only steps 2, 3 and 5 change. The buyer sees nothing different.

Steps and owners

  1. Bridge script Josh, programs-static repo: add the get-ga-ids handler to google_analytics_guidedtrack_trigger.js (12 lines, already written in the Aug 21 email and the ct-checkout README). It reads the _ga cookies and hands client_id and session_id back to GuidedTrack.
  2. GT programs Josh or Igor: at start, trigger get-ga-ids and store the two values; pass them to the Firebase checkout call (or route the checkout redirect through ct-checkout /checkout with cid and sid).
  3. Firebase Josh, dashboard repo: the three getCheckoutUrl functions accept ga_client_id and ga_session_id and write them into the session's metadata. Without a Firebase change, ct-checkout's /stamp-session does the same on the open session.
  4. Webhook Josh, dashboard repo, or ct-checkout: on checkout.session.completed, send the GA4 purchase with client_id, session_id, transaction_id (the payment intent), value in dollars, currency, items and engagement_time_msec. The existing sendGA4PurchaseEvent in the dashboard repo is never called, has no session_id or transaction_id, and its GA4 secret is not declared; fix it or use ct-checkout's sender.
  5. Subscribe program Josh: program 1pvomgo runs on www.guidedtrack.com, where no script runs, so step 1 cannot reach it. Publish it on programs.clearerthinking.org like the other paid flows.
  6. Renewals: send them as a separate event (subscription_renewal) with the client_id stamped on the Stripe Customer, not as purchase. Otherwise "(not set)" never goes away and the purchase count overstates new sales by roughly 2 to 1.
  7. Cut-over Igor: once a new Checkout Session shows ga_ metadata in Stripe and GA4 shows attributed purchases, uninstall Paytics the same day (both running means double counting). Fix the ct-checkout Vercel env or retire the project, depending on who ends up owning the webhook.

How to verify it worked

  • In Stripe, open the newest Checkout Session: metadata shows ga_client_id and ga_session_id.
  • In GA4 Realtime, the purchase appears within a minute of the payment (Measurement Protocol events show there when session_id and engagement_time_msec are included).
  • After 24 to 48 hours, the Events report for purchase shows real values under session source / medium. Renewals stay (not set) until step 6.
Do not: buy Paytics Premium (it lifts the cap but still has no way to know the buyer's numbers); change GA4 attribution or channel settings (the data is missing, not misfiled); rely on thank-you pages (impossible for the PDF and cognitive-test flows, and Stripe itself says the redirect is not guaranteed).
